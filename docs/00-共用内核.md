## 1. 需求模型

一句话：**用户画的是路径本身，不是模型。**

```
笔画 Stroke = {
  点序列 points[],
  起点事件 start: { io, level, delayMs },
  终点事件 end:   { io, level, delayMs },
}
```

这跟切片器的心智模型完全不同。切片器输入 STL、输出分层轮廓；我们输入手绘图元、输出笔画序列。**不要从「3D 打印」入手，这是激光切割 / 点胶类 CAM。**

三条不可动摇的约定：

1. **笔画是原子的。** 一条笔画内不做 IO 变化（否则它就该拆成两条）。
2. **两端事件各自独立。** 起点和终点可以是不同通道、不同电平、不同延时。
3. **延时是「事件之后」的时间，不是距离。** 界面单位统一 ms；需要换算成距离时由后处理器按 feed 算（`Δ = feed × ms/1000`）。

## 2. 数据模型

工程文件 JSON，三层嵌套。

```jsonc
{
  "version": 1,
  "units": { "length": "mm", "time": "ms" },
  "machine": {
    "name": "lc-diym",
    "travel": { "x": 200, "y": 200, "z": 100 },
    "softLimit": true,
    "hasHomeSwitch": false,
    "feedDefault": 600,      // mm/min，打印段
    "feedRapid": 6000,       // mm/min，空驶段
    "accel": 300             // mm/s²
  },
  "process": {
    "riseMs": 120,           // 开阀后驻留
    "tailMs": 80,            // 关阀后驻留
    "liftZ": 0.3,            // 抬针高度
    "liftFeed": 3000,
    "dwellBeforeClose": 0    // 终点前额外驻留（一般 0）
  },
  "layers": [
    {
      "id": "L1",
      "z": 0.4,
      "repeat": 1,
      "zStep": 0.4,
      "overrides": { "riseMs": 150 },   // 本层覆盖全局
      "strokes": [
        {
          "id": "s1",
          "points": [[10,10],[50,10],[50,40],[10,40]],
          "closed": true,
          "feed": 600,
          "kind": "contour",
          "start": { "io": 0, "level": 1, "delayMs": 120 },
          "end":   { "io": 0, "level": 0, "delayMs": 80 },
          "source": { "type": "rect", "x": 10, "y": 10, "w": 40, "h": 30 }
        }
      ]
    }
  ],
  "calibration": { "profileId": "gel-0.4mm-0.6MPa" }
}
```

**`source` 字段是必须的。** 存图元的原始描述，不只存离散点——否则用户改一个矩形宽度，你只能重新生成整段点，没法做「只改那个图元」的增量更新。编译产物标 `stale`，前端重算。

**坐标系：工程文件里 Y 向上**（和 G-code 一致），只在渲染时翻转。反过来做的话每次导出的图都是上下颠倒的，而且很难发现。

## 3. 四层管线

```
① 画布编辑器  →  图元（line/rect/circle/bezier/svg/text）
                        ↓ 编译（离散、填充、排序）
② 路径编译器  →  有序笔画列表
                        ↓ 后处理（插事件、插驻留、抬针）
③ 后处理器    →  G-code 文本（方言可插拔）
                        ↓ 下发（打包、窗口控制、重传）
④ 下发器      →  设备
```

每层可独立测试。②③ 之间是纯函数（笔画列表 → 文本），最适合写单元测试。

### ③ 后处理器的方言抽象

**这是「一套代码支持多种硬件」的关键。**

```ts
interface Dialect {
  name: string

  // 能力声明 —— 后处理器据此自动调整输出
  caps: {
    queuedIO: boolean      // IO 指令是否随运动排队执行
    arcs: boolean          // 是否支持 G2/G3
    multiCmdPerLine: boolean
    maxLineLen: number
    dwellUnit: 'ms' | 's'
  }

  header(machine, process): string[]
  strokeStart(stroke, pt, process): string[]
  strokeSegment(from, to, feed): string[]
  strokeEnd(stroke, pt, process): string[]
  footer(): string[]
}
```

**`caps.queuedIO` 是最重要的一个字段。** 它决定后处理器要不要自动插 `M400`：

| `queuedIO` | 含义 | 后处理器的行为 |
|---|---|---|
| `true` | IO 指令进规划器队列，按运动时刻执行 | 直接输出 `阀开 → G4 → G1`，时序精确 |
| `false` | IO 指令由命令解析器立即执行 | 自动在每个 IO 指令前插 `M400`，**强制停车换正确性** |

Klipper = `true`。Marlin / 自研板（待测）= 可能 `false`。

**这一个字段，就把「两套方案」的差异压缩成了配置。**

## 4. 笔画展开成什么（通用骨架）

```
; ── stroke s1 ──────────────────
<确保阀关>              ; 幂等，防上一条异常遗留
<空驶到起点>            ; 阀关着，可用快速
<下降到 z>
<开阀>                  ; start.io / start.level
<驻留 start.delayMs>    ; 等压力建立、墨咬住基底
<G1 到各点，恒速>       ; feed 不变
<G1 到终点前 Δ>         ; Δ = feed × tailMs/1000
<关阀>                  ; end.io / end.level
<驻留 end.delayMs>      ; 等余压泄掉
<抬针 liftZ>
```

**为什么关阀要放在「终点前 Δ」而不是终点后**：如果 IO 不能排队（`queuedIO=false`），你只能在机器停下后关阀；那关阀点必然在终点之后，多走的一段会拖出一道墨尾。所以要么在终点前切一刀停车关阀，要么接受拖尾。前者几何可控。

**驻留必须在关阀之后，不能在之前。** T-Code 论文（Nature Comms 2025）测出「停车瞬间会多挤一点」——先停再关，那点余量就留在原地鼓包；先关再停，余量在关阀后泄掉。

## 5. 标定：这是软件真正的资产

代码重写一天能搞定，参数表要几十次实验。**工程文件必须能存它。**

单独一个 `calibration.json`，按「材料 + 针径 + 气压」索引：

```jsonc
{
  "profiles": [
    {
      "id": "gel-0.4mm-0.6MPa",
      "material": "海藻酸钠 3%",
      "needle": 0.4,
      "pressure": 0.6,
      "riseMs": 120,
      "tailMs": 80,
      "lineWidth": 0.42,
      "maxFeed": 900,          // mm/min
      "minSegmentLen": 1.5,    // 见下方「无 look-ahead」约束
      "notes": "起点无拖尾，终点无断口"
    }
  ]
}
```

### 三组实验

**A · pre-flow 扫描**（阀先开、等、再走）
- 固定 F=600mm/min、长度 20mm
- `riseMs` 取 0 / 30 / 60 / 100 / 150 / 200 / 300
- 每档 5 条，量**起点宽度**（太短拖细尾，太长起点鼓包）

**B · post-flow 扫描**
- 固定 A 的最优值
- `tailMs` 取 0 / 30 / 60 / 100 / 150 / 200
- 量**终点**（太短断口或拉丝，太长鼓包）

**C · 线宽-速度关系**
- 固定最优 pre/post，F 取 300 / 480 / 600 / 900 / 1200
- 量线宽随速度的变化率
- 变化小 → 填充算法可放宽恒速约束；变化大 → 恒速是硬约束

75 条 20mm 短直线，一下午。产出的表比任何界面都有说服力：**「同一套参数打 50 条线，线宽标准差 < 5%」。**

### ⚠️ 无 look-ahead 的硬约束

协议只说「四轴按位移比例同步加减速」，没说有队列前瞻规划。如果没有，每条 `G1` 都从 0 加速到 F 再减到 0。

加速距离 = `F²/(2a)`。取 a=300mm/s²：

| F (mm/min) | F (mm/s) | 加速距离 |
|---|---|---|
| 300 | 5 | 0.04 mm |
| 600 | 10 | 0.17 mm |
| 900 | 15 | 0.38 mm |
| 1200 | 20 | 0.67 mm |

**结论：单段长度至少要 1.5mm 以上**，越短实际平均速度越低、线宽越粗。这是 v1 的硬性约束，写进填充算法的参数校验里。

## 6. 仿真：板子没到也能开发

### 6.1 mock 板（必做，最高优先）

不是「假装是打印机」，是**照着协议文档假扮那块板子**，逐字节一致。上位机改一个 IP 就在 mock 和真机之间切换。

**核心是虚拟时钟**：不按真实速率 sleep。`G1 X50 F3000` 立刻算出耗时（含加减速），把完成事件排在虚拟时间 T+1.0s。10 小时任务几秒跑完。

**回包时序必须对**（最容易写错）：
- 收到包、解析出行 → 立刻回 `queued #N (M pending)`
- 同一时刻回 echo 包
- 等虚拟时间到 → 单独回 `E000`
- **绝不能在收到 G1 时就回 E000**

**必须实现的错误路径**：队列满 E020（丢行）、估算 >60s E010、软限位越界 E010、未知指令 E009、可注入丢包/乱序/抖动。

**产出两条时间线**：`position.csv`（每 1ms 一行 t,x,y,z,vx,vy）和 `io.csv`（每次变化的 t,channel,level）。

监听 `127.0.0.1:5000`，省掉在开发机上配 `192.168.0.0/24` 网卡的麻烦。

### 6.2 渲染器三视图（缺一不可）

1. **整体俯视**——出料段实线加粗、空驶段虚线、驻留点画圆点（半径按时长）。看图形对不对。
2. **时间轴**——IO 方波 + 速度曲线 + 位置曲线共用横轴。看「阀开的时候机器在不在动」。
3. **单笔画放大**——把起点/终点各 300ms 拉开放大，位置曲线和 IO 边沿叠在一起。

**第 3 个视图别的软件都不给你，因为别的软件没有「阀」这个概念。** 这是你调 Δ 的主视图：Δ 的本质就是「IO 边沿和笔画端点之间的水平距离」，这个视图能直接读出偏了多少。

### 6.3 现成工具（省力但不够用）

- **gcode2image**（MIT，`pip install gcode2image`）：像素级 2D 渲染，`--showG0` 画空驶、`--incremental` 显示重复写、`--showorigin --grid` 出网格。不认识 `M121` 但能验证几何。**白送的核对器。**
- **CAMotics**（GPL-2，铣削仿真）：只能验证几何，验证不了工艺。它假设刀具，不理解阀。
- **NC Viewer**（网页）：粘贴即看，零配置。

**都不该替代自写渲染器**——它们的语义模型里没有「阀开/关」。

### 6.4 不要做的：固件级仿真

Marlin Simulator / grbl-sim / Renode 都要跑固件二进制，而你手上只有协议文档。i.MX RT1170 的 ENET 和 TMC5160（外挂 SPI）模型不全，就算跑起来电机也不会动。

**协议文档本身就是规格书**，mock 板在这个维度上 100% 保真。

## 7. 实施顺序

| 阶段 | 做什么 | 需要硬件 | 产出 |
|---|---|---|---|
| 0 | mock 板 + 时间线导出 | 否 | 用协议 §9.1–9.6 示例会话做断言，逐字节对上 |
| 1 | 笔画 → G-code 编译器 + 渲染器 | 否 | 手写格栅块工程，出 G-code，出三视图 |
| 2 | Web 编辑器（画布/图元/填充/事件面板） | 否 | 能画、能改、能导出 |
| 3 | 真机标定 | 是 | 参数表 |

**0 和 1 不会在硬件到了之后废弃**——它们会变成回归测试。这段时间没有板子，它们就是唯一的「真机」。

## 8. 两套方案共用什么、不同什么

| 层 | 共用 | 不同 |
|---|---|---|
| 编辑器 | ✅ 完全共用 | — |
| 几何/填充/排序 | ✅ 完全共用 | — |
| 笔画数据模型 | ✅ 完全共用 | — |
| 标定表 | ✅ 完全共用 | 但数值不同（不同机器加速度、针径） |
| 后处理器骨架 | ✅ 共用 | **方言实现不同** |
| 下发器 | ❌ | UDP 报文 / 串口 / Moonraker HTTP |
| mock 板 | ❌ | 各模拟各的 |

所以：**共用内核 = 文档 00 的全部内容**。01 和 02 只写「方言实现 + 硬件改造 + 时序可信度 + 限制」。
