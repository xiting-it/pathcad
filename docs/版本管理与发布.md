# 版本管理与发布流程

> 面向开发与运维。目标是**任何时刻都能回答三个问题**：
> 这个产物是哪个版本？它对应哪份代码？它改了什么？

---

## 1. 版本号规则

标准 [SemVer](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH[-预发布][+构建]`

### 什么时候升哪一位

| 位 | 触发条件 | 例子 |
|---|---|---|
| **MAJOR** | **不兼容**变更：工程文件格式变了、接口签名变了、用户数据需要迁移 | `1.4.0` → `2.0.0` |
| **MINOR** | 向下兼容的**新功能** | `1.4.0` → `1.5.0` |
| **PATCH** | 向下兼容的**问题修正**，不加功能 | `1.4.0` → `1.4.1` |

**判断口诀**：旧版本的工程文件能否被新版本直接打开？
- 能 → 不是 MAJOR
- 不能 → 是 MAJOR

### 预发布标识

| 写法 | 含义 | 适用 |
|---|---|---|
| `1.4.0-alpha.1` | 内部开发版，功能不全 | 只给自己 |
| `1.4.0-beta.1` | 功能完整，待验证 | 给合作方试用 |
| `1.4.0-rc.1` | 候选发布，只修 bug | 给金主/客户预览 |
| `1.4.0` | 正式版 | 交付 |

同一预发布号的递增用 `.1`、`.2`……；进入下一阶段时重置。

### 不要做的事

- ❌ 不要复用已发布的版本号（发出去的号就是历史）
- ❌ 不要在 PATCH 里加功能（会让依赖方无法判断风险）
- ❌ 不要跳过预发布直接从 `1.3` 跳到 `1.5` 正式版
- ❌ 不要用 `beta1.3.12` 这种非标准写法（1.4.0 之前的遗留，已废弃）

## 2. 版本号在哪里改

**唯一数据源：`app/version.py`**

```python
APP_NAME = "CAM-B"
VERSION  = "1.4.0-beta.1"        # ← 只改这一行
```

改完后以下位置自动跟着变，**不要手动去改别处的版本号**：

| 位置 | 值来源 |
|---|---|
| 打包产物名 `CAM-B-<版本>-dist.exe` | `DIST_NAME` |
| 启动横幅 | `main.py` 读 `VERSION` |
| 页面标题 / 状态栏 / 关于框 | `GET /api/version` |
| FastAPI 元信息 | `app.server` |
| G-code 注释 | `app.dialects` |
| `dist/README.txt` | `dev/_build_docs.py` 替换占位符 |

**校验**：`parse_version()` 会在格式不对时抛 `ValueError`，打包直接失败——避免悄悄产出坏版本号。

```bash
python -c "from app.version import *; print(VERSION, DIST_NAME, parse_version(), channel())"
```

## 3. 产物命名

```
CAM-B-<版本>-dist.exe
```

| 段 | 含义 |
|---|---|
| `CAM-B` | 产品名 |
| `<版本>` | 完整 SemVer，含预发布标识 |
| `dist` | 分发版（区别于开发环境的直接运行） |

示例：`CAM-B-1.4.0-beta.1-dist.exe`

**为什么文件名带版本**：拿到一个 exe，不用打开就能知道是哪一版。这在多方协作、多版本并行时是刚需。

## 4. 发布流程

按顺序执行，**不要跳步**。

### 4.1 准备

```bash
# 1. 确认工作区干净
git status                      # 应为空

# 2. 确认版本号与 CHANGELOG 一致
python -c "from app.version import VERSION; print(VERSION)"

# 3. 跑全部测试
PYTHONPATH=. python dev/_infill_test.py
PYTHONPATH=. python dev/_fillscan_test.py
PYTHONPATH=. python dev/_serial_test.py

# 4. 检查前端语法与 HTML 结构
node --check web/app.js
node --check web/menubar.js
node --check web/panel.js
node --check web/grid.js
node --check web/logview.js
grep -o 'id="[^"]*"' web/index.html | sort | uniq -d    # 应为空
```

### 4.2 打包（顺序不能反）

```bash
# ① 打包（会清空 dist/）
python build.py

# ② 生成文档、README、示例模型
python dev/_build_docs.py
```

> **为什么顺序不能反**：`build.py` 的 `clean()` 会 `rmtree(dist)`，先跑文档会被删光。

### 4.3 验证打包产物

**必须测打包后的 exe，不是开发服务器。**

```bash
./dist/CAM-B-<版本>-dist.exe
```

验证清单：

- [ ] 启动横幅显示正确版本
- [ ] 页面标题 / 状态栏 / 关于框版本一致
- [ ] 新建工程后 `S.project.app === 'cam-b'`
- [ ] 载入示例 → 生成 G-code，笔画数与预期一致
- [ ] 3D 预览有内容
- [ ] 模拟板能完整发送
- [ ] 浏览器控制台零报错
- [ ] `dist/` 结构完整：exe + README.txt + 文档/ + 示例模型/

### 4.4 提交与打标签

```bash
git add -A
git commit -m "chore(release): v<版本>"
git tag -a v<版本> -m "<版本> 发布"
git push origin main
git push origin v<版本>
```

**标签规范**：`v<版本>`，带 `v` 前缀，与 `version.py` 的 `VERSION` 完全一致（含预发布标识）。

| 正确 | 错误 |
|---|---|
| `v1.4.0-beta.1` | `1.4.0-beta.1`（少 v） |
| `v1.4.0` | `v1.4`（少一位） |

### 4.5 发布附件

exe 不进仓库（`.gitignore` 已排除 `dist/`），通过 GitHub Release 附加。

```
Release 标题：CAM-B 1.4.0-beta.1
附件：CAM-B-1.4.0-beta.1-dist.exe
说明：从 CHANGELOG 对应段落复制
```

## 5. 提交信息规范

采用 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)：

```
<类型>[(范围)][!]: <描述>

[正文]
```

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 问题修正 |
| `docs` | 只改文档 |
| `refactor` | 重构，不改变外部行为 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建、依赖、杂务 |
| `feat!` / `BREAKING CHANGE` | 标记不兼容变更 |

示例：

```
feat(dialect): 新增 H5 方言，支持四轴与 4 路 IO

fix(ui): 导入三维模型后摘要卡层数算错

feat!: 产品更名为 CAM-B，版本改用 SemVer
```

**为什么要求规范**：CHANGELOG 可以直接从提交历史生成，不用手写。

## 6. CHANGELOG 维护

文件：`CHANGELOG.md`，格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)。

### 开发时

在 `## [未发布]` 下面随手加，按类型分组：

```markdown
## [未发布]

### 新增
- xxx

### 修复
- yyy
```

### 发版时

把 `## [未发布]` 的内容移到新版本标题下，并补上日期：

```markdown
## [1.5.0] - 2026-12-01

### 新增
- xxx
```

### 分类用词

| 用词 | 含义 |
|---|---|
| `新增` | 新功能 |
| `变更` | 对现有功能的调整 |
| `修复` | 问题修正 |
| `移除` | 删掉的功能 |
| `安全` | 安全相关 |
| `不兼容` | 破坏性变更，升级需注意 |

**写给人看**：写"用户会感知到什么"，不要写"改了哪个函数"。

- ✅ `修复 导入三维模型后摘要卡层数显示为 1`
- ❌ `修复 refreshSummary 未处理多图层分支`

## 7. 分支策略

当前规模用**主干开发**即可：

```
main ──●──●──●──●──●──►  始终可发布
         \        /
          ●──●──●       功能分支（可选）
```

- `main` 始终处于可发布状态
- 大改动开功能分支，完成后合回
- 每个发布打 tag
- **不做长期存在的 develop 分支**（单人/小团队没必要，只会增加合并成本）

## 8. 版本兼容承诺

面向团队与合作方，**不是公开 SDK**，因此：

| 承诺级别 | 内容 |
|---|---|
| ✅ 保证 | 同一 MINOR 版本内，工程文件可互读 |
| ✅ 保证 | 旧工程文件在新版本能打开（自动迁移） |
| ⚠️ 尽力 | 方言接口签名在 MINOR 内不变 |
| ❌ 不保证 | 跨 MAJOR 的接口兼容 |
| ❌ 不保证 | Python 内部模块的导入路径稳定（`app.xxx` 可能调整） |

**升级建议**：MAJOR 升级前先在副本上验证，工程文件先备份。

## 9. 常见事故与处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 打包报 `WinError 5` | 上一次的 exe 还在运行 | 杀进程后重打（`build.py` 已自动通配杀） |
| `dist/` 里没有文档 | 先跑了文档生成再打包 | 按 4.2 的顺序重来 |
| 产物名版本不对 | 改了别处的版本没改 `version.py` | 只在 `version.py` 改 |
| 打包后界面还是旧版本号 | 浏览器缓存，或改的是开发服务器 | 确认打开的是打包产物；Ctrl+F5 |
| tag 与版本号不一致 | 打标签时手打错了 | `git tag -d` 删掉重打（未推送时） |
