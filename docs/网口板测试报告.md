# 网口板（i.MX RT1170）测试报告

> 测试日期：2026-11-16
> 板卡：LCSystem 网口板，i.MX RT1170 + TMC5160 × 4
> 连接：UDP `192.168.0.102:5000`
> 电脑网卡：以太网 2，静态 `192.168.0.100/24`
> 状态：**空载，未接限位开关，不接气阀**

## 一、IO 控制（M121）

![IO 控制实测](nic/01-io-control.png)

`IOOUT` 掩码随 `M121` 正确变化，8 路可单独或批量控制：

| 指令 | 应答 | IOOUT | 说明 |
|---|---|---|---|
| `M121 U0 V0` | E000 | 0x00 | 全关 |
| `M121 U0 V1` | E000 | 0x01 | 开第 0 路 |
| `M121 U0 V0` | E000 | 0x00 | 关第 0 路 |
| `M121 U1 V1` | E000 | 0x02 | 开第 1 路 |
| `M121 U1 V0` | E000 | 0x00 | 关第 1 路 |
| `M121 V255` | E000 | 0xFF | 8 路一次全开 |
| `M121 V0` | E000 | 0x00 | 8 路一次全关 |

**结论：`M121` 可用，能控制气阀。这是 F1 串口板做不到的。**

`M120` 读回的三组掩码：

| 掩码 | 含义 |
|---|---|
| `IOIN 0xFF` | 8 路输入全为高（未接限位时的悬空状态） |
| `IOORG 0x40` | 原点开关位图（bit6，对应 Z 轴附近） |
| `IOOUT 0x00` | 输出全关 |

## 二、运动控制

| 指令 | 应答 | 实测坐标 | 耗时 |
|---|---|---|---|
| `G0 X10 Y10 F3000` | E000 | (10.00, 10.00, 0.00) | 0.59s |
| `G1 X20 Y20 F600` | E000 | (20.00, 20.00, 0.00) | 1.29s |
| `G1 X0 Y0 F600` | E000 | (0.00, 0.00, 0.00) | 2.39s |

坐标误差 < 0.01mm，速度准确。

`G1 X20 Y20 F600` 的理论耗时是 √(20²+20²)/10 ≈ 2.83s，实测 1.29s——**差了一倍**。

原因：这条指令是两轴同时动的对角线，实际位移是 √(20²+20²) ≈ 28.3mm，而不是 20mm。板子按 DDA 插补以最快轴的速度计算，所以实际速度是 20/2.83 ≈ 7.07mm/s... 

等一下，28.3mm ÷ 1.29s ≈ 21.9mm/s > 10mm/s，**超速了**。

这说明 `F` 值在板子里可能被解释为「最快轴的速度」而不是「合速度」。对 DIW 来说这会影响线宽一致性，需要注意：**画对角线时的实际速度比单轴快**。

⚠️ **建议**：跟朋友确认 `F` 的语义（合速度还是最快轴）。如果是后者，编译器在生成对角线时要按比例放大 `F` 值补偿。

## 三、上位机延时精度

![延时精度](nic/02-dwell-precision.png)

这块板**不支持 `G4`**，所以延时由上位机 `sleep` 实现。实测：

| 目标 | 实测均值 | 偏差 | 抖动 σ |
|---|---|---|---|
| 100 ms | 100.4 ms | +0.4 ms | 0.2 ms |
| 200 ms | 200.2 ms | +0.2 ms | 0.1 ms |
| 500 ms | 500.4 ms | +0.4 ms | 0.1 ms |

**偏差不到 1ms，抖动 0.2ms**，远好于预期。

之前预估会有 5-20ms 误差（GIL、调度、UDP 往返），实测远好于预期。原因是：sleep 是在**收到 E000 之后**才开始计时的，这时板子已经空了，UDP 往返的抖动不会叠加。

**结论：`host` 模式的延时精度完全够用**，DIW 的 60-200ms 驻留没问题。

## 四、队列与 G4

### 队列深度

连发 20 条 `M114`（不等回包），**没有触发 E020**。

这说明队列深度比文档写的 8 要大，或者查询类指令不占队列。之前 F1 测试时的 E020 是另一种情况（G4 卡死导致）。

### `G4` 不支持

```
发 G4 P100 → 无回包（10.2s 超时）
随后 M114 → 无回包
连续 6 次 M114 → 全部无回包
```

**发 `G4` 会彻底卡死板子**，只能断电重启。

这就是为什么延时要由上位机实现（`dwell="host"`）。

![G4 卡死](nic/03-g4-blocked.png)

## 五、对 CAM-B 的实现要求

| 能力 | 实现方式 |
|---|---|
| IO 控制 | `M121 U<n> V<0/1>`，直接下发 |
| 延时 | **上位机 sleep**（`dwell="host"`），编译器输出 `delays[]` |
| 驻留时长 | 挂在 `M121` 那行的 `delays[i]` 上 |
| 运动同步 | 一发一等（等 E000 再发下一条） |
| 进度估算 | 按已发笔画数 / 总笔画数 |

**已实现**：

```python
# dialects.py — caps.dwell = "host"
# compiler.py — delays[i] 挂在产生延时的那行上
# link.py — JobRunner 按 delays[i] sleep（在等 E000 之后）
```

**实测时序**（100ms 驻留）：

```
t=0        发 M121 U0 V1
t=0.001    收到 E000
t=0.001    sleep 开始
t=0.100    sleep 结束（偏差 0.4ms）
t=0.101    发下一条 G1
```

## 六、需要向硬件方确认的问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | **F 的语义是合速度还是最快轴速度？** | 实测对角线超速，影响线宽一致性 |
| 2 | `M121` 是排队执行还是立即执行？ | 决定开阀时机与运动的相对位置 |
| 3 | `IOOUT` 掉电后的默认状态？ | 关阀还是开阀（安全相关） |
| 4 | 队列真实深度是多少？ | 文档写 8，实测连发 20 条没报 E020 |
| 5 | `G02` 圆弧的效率？ | F1 慢 2.7 倍，网口板未测 |
